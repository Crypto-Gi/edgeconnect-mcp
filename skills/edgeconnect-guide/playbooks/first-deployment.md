# First deployment: interview, recommend, build

> **Reference only.** Every operation below was run on Orchestrator 9.7.1 (ECOS 9.6.2.1 lab appliances and an ECOS 9.6.4.0 production appliance, test objects only) between 2026-10-16 and 2026-10-18. This playbook writes nothing itself: each build phase hands off to another playbook or to the Orchestrator UI. Your version and configuration can behave differently: read first, show the change, get a yes, and verify each step yourself.

Guide a user through a first EdgeConnect deployment, or a review of a young one: learn what exists, ask what they need, recommend the field best practices for their answers, then build it one phase at a time with their permission. Background: [deployment best practices](../cards/deployment-best-practices.md).

## Before you start
- Ask, never assume. Ask a few questions at a time, in the order of step 2, and skip any the step 1 reads already answer. If the user does not know an answer, give the recommended default and say it is one.
- On a shared or already populated Orchestrator, build only new objects with a name prefix the user picks, in your own template groups; never edit the Default Template Group or overlays, labels and zones other sites use.
- Keep it simple: build only what the answers require. Every write goes through the playbook it names, with the change shown and a yes before each `api_write`.
- Writes need `<nickname>_mcp_writes=true` for that Orchestrator in the server's dotenv file. On a read-only Orchestrator, still run the interview and the plan; the user builds from it in the UI.
- Some items have no MCP route in this guide (approving appliances, pushing a deployment, users and authentication, licensing and the account key, backups, custom applications, turning segmentation on, routes, management services). For those give the UI path from the card and wait for the user to say it is done.

## Steps
1. Read what exists. Call `api_get` on `GET /gms/versions`, `GET /appliance`, `GET /appliance/discovered`, `GET /gms/group`, `GET /template/templateGroups` (`namesOnly` true), `GET /template/templateGroupsPriorities`, `GET /gms/interfaceLabels`, `GET /gms/overlays/config`, `GET /vrf/config/segments`, `GET /zones`, `GET /overlayManagerProperties`, `GET /loopbackOrch/pool` and `GET /gms/backup` (404 means no backup is set up). Tell the user in a few lines what is there: version, appliance count and roles, labels, overlays, segments, zones, template groups, backup or not.
2. Interview. Ask in this order, a few questions per message, and note each answer. Check answers against the step 1 reads with `api_get` where they overlap (for example a site count against `GET /appliance`).
   - Orchestrator: cloud service or self-hosted; who logs in (SSO, TACACS or RADIUS); where backups go if self-hosted.
   - Fabric: how many sites, which are hubs or data centers, any cloud hubs; mesh, hub and spoke, or regional; how many regions.
   - Circuits per site: internet, MPLS, LTE; static IP or DHCP; NAT or CG-NAT; real bandwidth; a firewall in front of the EC WAN or sharing the circuit.
   - LAN: EC as the layer 3 gateway (VLANs) or a routing link to a core switch or router; BGP, OSPF or static; DHCP server, relay or neither.
   - HA: one appliance or a pair per site; EdgeHA or VRRP.
   - Segments and security: guest, IoT, PCI or other separated traffic; zones; IDS/IPS (advanced license); security scanners on the network.
   - Internet: local breakout or backhaul to a hub; cloud security service (Zscaler, Netskope); key SaaS.
   - Operations: syslog, SNMP, NTP, DNS servers, monitoring tools, alarm destinations.
3. Recommend. Write a short design summary: for each answer, the recommended choice in one line with the card that explains it (start from the [deployment best practices](../cards/deployment-best-practices.md) key facts, then [wan circuits](../cards/wan-circuits-shaper.md), [overlays](../cards/overlays-bio.md), [segmentation](../cards/segmentation.md), [security zones](../cards/security-zones-firewall.md), [VRRP and HA](../cards/vrrp-ha.md), [BGP](../cards/bgp.md), [internet breakout](../cards/internet-breakout-saas.md)). Flag every answer that goes against field advice (EC WAN behind a layer 7 firewall, no DHCP circuit at a spoke, the same WAN label twice, mesh sites without static IPs) and say why; with a firewall in front of the EC, give its outbound rules from the card right there, the IPSLA ICMP included. Add the readiness list for other teams: the firewall rules, IP ranges (ASN pool, loopbacks, MPLS), collectors and accounts from the card. Use `find_operations` to check whether each build item has an operation; mark the rest as UI. Ask the user to confirm or change the design.
4. Plan the build. Turn the design into phases in this order, each with its playbook or UI path, and show the list: Orchestrator settings and backup (read with `api_get` `GET /overlayManagerProperties` and `GET /gms/backup`; changes in the UI, see [orchestrator settings](../cards/orchestrator-settings-backup.md)); labels ([interface labels](interface-labels-wan.md)); the default template group and any subset groups ([template group](template-group.md)); segments ([add segment](add-segment.md)) after the user turns segmentation on in the UI; zones and rules ([security zones](security-zones-rule.md)); overlays ([business intent overlay](business-intent-overlay.md)); preconfiguration and onboarding ([onboard appliance](onboard-appliance.md)), hub first, then one branch; routing ([BGP neighbors](bgp-neighbors.md), or the UI for OSPF and static routes). For each write the plan uses, call `describe_operation` and note its body. Get a yes for the whole plan, then a yes again at the start of each phase.
5. Build one phase at a time by running its playbook from its first step: it reads, shows the change, waits for a yes, calls `api_write`, and reads back. After each phase, report the result to the user in a few lines and ask before starting the next. Stop on any unexpected result and show it.
6. UI-only items: give the user the UI path from the card and the values from the design, and wait until they say it is done. Then confirm with `api_get`: `GET /appliance/approved` after an approval, `GET /deployment` (`nePk`) after a deployment push, `GET /mgmtServices` (`nePk`) after a management services change.
7. Check tunnels once the hub and the first branch are in. Call `api_get` on `GET /tunnels2/physical` (`nePk`) for underlay tunnels first, then `GET /tunnels2/bonded` (`nePk`) for overlays. Underlay must be up before overlays can be; Idle is normal for a quiet tunnel. If a tunnel stays down, follow [tunnel down](tunnel-down.md).
8. Hand over. Call `api_get` on `GET /alarm/summary` and show any open alarms. Give the user the final design summary, what was built, what they still do in the UI, and suggest a backup and the [upgrade and maintenance](upgrade-maintenance.md) checklists before the next sites.

## Verify
- `GET /appliance` shows each new appliance reachable (`state` 1) with the hostname and group from the design.
- `GET /template/applianceAssociation` (`nePk`) lists the template groups from the plan; `GET /gms/interfaceLabels` and `GET /gms/overlays/config` hold the labels and overlays from the design.
- `GET /tunnels2/physical` and `GET /tunnels2/bonded` (`nePk`) show tunnels up between the hub and the branch.
- `GET /alarm/summary` has no new critical alarms.
