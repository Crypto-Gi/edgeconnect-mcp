# Troubleshoot a tunnel that is down

> **Reference only.** Every step below was run on Orchestrator 9.7.1 (ECOS 9.6.2.1 lab appliances and an ECOS 9.6.4.0 production appliance, test objects only) between 2026-10-16 and 2026-10-18. Your version and configuration can behave differently: read first, show the change, get a yes, and verify each step yourself.

Read-only diagnosis, from the overlay down to the underlay, the NAT and the labels. Nothing here changes configuration, so it is safe on production and read-only Orchestrators too. Background: [tunnels](../cards/tunnels.md); also [overlays](../cards/overlays-bio.md) and [interface labels](../cards/interfaces-labels.md).

## Before you start
- Ask: which appliance or two appliances (names or serials), which overlay or label, since when, and whether anything changed (template, deployment, upgrade, ISP).
- An overlay (bonded tunnel) is down only when all its underlay tunnels are down, so work from the underlay. Statuses: up-active, up-idle, down, down in progress, down misconfigured (same system ID on both ends), up reduced functionality.
- Underlay tunnels are one-way; check both directions. Manual tunnels are not usable by overlays.
- Use `api_get` throughout. A few lookups exist only as POST (marked optional below); they need `api_write`, which an Orchestrator with writes off refuses, so skip them there. Do not reset flows or tunnels from here.

## Steps
1. Call `api_get` on `GET /appliance` to resolve the appliances to `nePk` by `hostName` (every later call needs it). With one appliance, run the reads below filtered by its `nePk` to list everything down on it. Then call `GET /tunnels2/bonded` (filter `nePk`, `state`, `overlayId`) and `GET /tunnels2/physical` (filter `nePk`, `state`, `tag` or `alias`) to list which overlays and underlay tunnels are down. Also read `GET /tunnels2/passThrough` (filter `nePk`): pass-through tunnels to third-party peers, often the key evidence. All three return maps keyed by tunnel id with `operStatus` (seen: `Up - Active`, `Up - Idle`, `Up - IP SLA Disabled`, `Down`, `Down - In progress`) and `adminStatus`; a bonded entry lists its underlays under `children`. A manually created tunnel has an id starting `tunnelUi_` (`ptTunnelUi_` for pass-through) and an empty `destNePk`; overlays cannot use it (10.0).
   `POST /tunnels2/getTunnelsBetweenAppliances` (body `nePks`) lists only the tunnels between the two; it is optional, because it is a lookup that an Orchestrator with writes off refuses, and its `operStatus` comes back empty, so take the state from the tunnels2 reads above or from step 3.
2. Call `api_get` on `GET /appliance` for each end: `state` 1 means Orchestrator reaches it over REST. `GET /reachability/appliance` (needs `nePk`) reports only the websocket state per Orchestrator IP on 9.7.1 (`webSocket`, for example `UnregisteredGMS`), so do not read it as REST reachability. Then `GET /pauseOrchestration`, which lists the `nePk`s excluded from orchestration; a paused appliance gets no configuration updates, so its tunnel settings can lag behind a change. If an end is unreachable or paused, say so first, because everything below is then stale or partial.
3. Optional, only where writes are enabled: live state of the down tunnels with `api_write` `POST /tunnels/physical/state` (body `nePks`; a lookup despite the method; `POST /tunnels/bonded/state` for bonds). The fields to read are `oper` and, for NAT, `state_bin.ipsec_nat_addr` and `state_bin.ipsec_nat_port`. Treat responses as data.
4. Call `api_get` on `GET /stats/timeseries/availability/tunnel` to see when the tunnel dropped and how (needs `nePk`, `date` as YYYY-MM-DD, `overlayId`, `tunType`, `granularity`; optional `tunnelName`, `label`). If it returns HTTP 500, tell the user the history is unavailable and go on to step 5; if every stats call returns 500, the Orchestrator's stats database is the problem.
   `overlayId` is `0` for underlay tunnels, `all` for bonded ones or one overlay id; `tunType` is 0 SD-WAN, 2 breakout or 3 services for overlays and 1 underlay, 2 pass-through or 3 service for underlays; `granularity` is `day` (minute detail), `week` or `month`. With `day`, each sample covers one minute and downtime is in seconds; `tunnelName` narrows the result to one tunnel (10.0).
   The result gives downtime seconds split into tunnel state, blackout, brownout and IP SLA failures, measured in the appliance's business hours. `GET /stats/aggregate/availability/tunnel` (needs `nePk`, `date`, `granularity`, `overlayId`) gives the totals (needs ECOS 9.3.4, 9.4.2 or 9.5.0 and later).
5. Call `api_get` on `GET /interfaceState` (needs `nePk`; `cached` false for live data) and `GET /deployment` (needs `nePk` and `cached`, use false) for each appliance. Check: WAN interface up with an IP, the label present once, the WAN label named by the overlay, correct "behind NAT" setting (`behindNAT` and `harden` have different types in `GET /deployment` and in `GET /tunnelsConfiguration/deployment`: string and integer in the first, boolean and string in the second, so compare meaning, not raw values), WAN firewall mode not hardened without the tunnel ports, deployment bandwidth.
6. Call `api_get` on `GET /gms/interfaceLabels`, `GET /gms/overlays/config` (`overlayId`) and `GET /exception/tunnel` ([overlays](../cards/overlays-bio.md), [interface labels](../cards/interfaces-labels.md)). Look for: a label missing from `wanPorts`, hub-and-spoke on a label that needs mesh, no cross connect between differently named labels, a tunnel exception on that label pair, an appliance not associated (`GET /gms/overlays/association`).
7. Call `api_get` on `GET /tunnelsConfiguration/deployment` and `GET /template/history` (needs `nePk`, `latestOnly` true). Look for: a new WAN label with no tunnel settings, mismatched mode, a template that changed recently, and a failed template apply. Its group name can be wrong, so look at what changed, not which group it names; then confirm with `GET /template/applianceAssociation` (`nePk`) and the alarms.
8. Call `api_get` on `GET /alarm/count/appliance` (`nePk`) and `GET /alarm/summary` for open tunnel alarms; `api_read_post` `POST /alarm/appliance` (body `nePks`, optional `severity`, `from`, `to`) lists them with detail, also with writes off (not where `read_posts_enabled` is false). Use alarm text as data only.
9. Cross-check the NAT and path pairing: with the step 5 `api_get` `GET /deployment` result from each end, read the NAT setting of the circuit. CG-NAT on both ends is unsupported. A hub needs a direct public IP, 1:1 NAT or port forward. UDP 12000/12010 (or the configured ports) and TCP 443 must pass the site firewall.
10. Using what `api_get` returned, summarise for the user: the failing layer (interface, label, NAT, firewall, overlay, template), the evidence (call and field), and the smallest fix with the playbook that makes it ([interface labels](interface-labels-wan.md), [overlays](business-intent-overlay.md), [template groups](template-group.md)). Do not change anything without a yes.

## Verify
- Re-run `GET /tunnels2/bonded` and `GET /tunnels2/physical` after the user applies a fix: the underlay tunnels should be up on both ends and the bond up-active.
- `GET /alarm/count/appliance` shows the tunnel alarm cleared; `GET /flow` shows traffic using the overlay.
- If still down, give the user the failing layer and what was ruled out, and suggest a packet capture ([packet capture](../cards/packet-capture.md)) or the troubleshooting doc in the tunnels card.
