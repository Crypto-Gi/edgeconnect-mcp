# Set up security zones and a firewall rule

> **Reference only.** Every step below was run on Orchestrator 9.7.1 (ECOS 9.6.2.1 lab appliances and an ECOS 9.6.4.0 production appliance, test objects only) between 2026-10-16 and 2026-10-18. Your version and configuration can behave differently: read first, show the change, get a yes, and verify each step yourself.

Add a firewall zone, add a rule between two zones, and prepare the deployment that moves an interface into the zone. Zones and segment security policies are whole-collection writes. Background: [security zones](../cards/security-zones-firewall.md).

## Before you start
- **Never post a body that holds only the new rule or one zone pair.** `POST /vrf/config/securityPolicies` with `merge` false replaces every zone pair of the segment pair; on the lab a one-pair body deleted all the sibling pairs. Step 5 builds the body from the whole `data` object read in step 1.
- Zone names: 16 characters or fewer, letters, digits and `_` only, not `Default`. Create the most used zones first, because order cannot change.
- Same-zone traffic is allowed and different-zone traffic is dropped until a policy says otherwise. Moving an interface into a new zone cuts it off from everything still in Default, so do that last, in a window.
- Pushing the deployment is not covered by this guide; apply it in the Orchestrator UI. This playbook validates the interface move; the user pushes it.
- With segmentation on, rules are per segment pair (`srcSeg_dstSeg`) and a templated zone policy only affects the default segment: see [segmentation](../cards/segmentation.md). Without it, rules are the `securityMaps` template in a template group.
- Collect: zone name, the interface to move (appliance `nePk`, interface), source and destination zone, the match (ACL, subnets, protocol, port, application), action (allow, deny, inspect), priority.
- Lab: zone `ztest_zone`; a deny rule for `192.0.2.0/24` (documentation range) at priority 5000.

## Steps
1. Call `api_get` on `GET /vrf/config/enable` first: it decides the path (segmentation on means per-segment-pair policies, off means the `securityMaps` template of a template group). Then `GET /zones` without `allVRFZones` (the global list, ids 1 and up with no Default 0; it is the base of step 3), `GET /zones/nextId`, `GET /zones/vrfSegmentZonesMap`, `GET /vrf/config/securityPoliciesSegments` (the `srcSeg_dstSeg` keys), and for the pair you will change `GET /vrf/config/securityPolicies` (needs `map`): keep its entire `data` object, every zone pair in it, because step 5 posts it back. Also `GET /securityMaps` (needs `nePk`) for the appliance view, and `GET /appliance/rest` with `nePk` and `url` `deployment` for step 4. With segmentation off, also read `GET /template/applianceAssociation` (`nePk`), then `GET /template/templateGroups` and `GET /template/templateSelection` with the `templateGroup` you will change. Keep the zone list, the policy pair (or the template group body and selection) and the deployment as the rollback snapshot.
2. Call `describe_operation` on `POST /zones` (needs `deleteDependencies`; body is the whole zone map keyed by id) and `POST /vrf/config/securityPolicies` (needs `map`; body `data`, `options`, `settings`; optional `comment`).
3. Add the zone: the body is the global list from `GET /zones` without `allVRFZones` plus the new zone at the id from `GET /zones/nextId`, for example `{"1": {"name": "..."}, "<nextId>": {"name": "ztest_zone"}}`. Leaving a zone out deletes it, and never post the `allVRFZones` view. Show the user the full map; after a yes call `api_write` `POST /zones` with `deleteDependencies` false, then `GET /zones` to confirm. With segmentation on, the Orchestrator then creates the zone once per segment, with consecutive ids (see `GET /zones/vrfSegmentZonesMap`). Zone ids are not reused.
4. Optional interface move (skip it for a pure rule test): with the `api_get` `GET /appliance/rest` (`url` `deployment`) object from step 1, change the `zone` field (an integer zone id, 0 meaning no zone; `sysConfig.zones[]` maps ids to names as `{"id": "<string>", "name": "..."}`) of that `modeIfs[].applianceIPs[]` entry, keep every other interface, and check it with `api_write` `POST /deployment/validate` (needs `nePk`; body `sysConfig`, `modeIfs`, `dpRoutes`). It answers `{"err": null, "rebootRequired": bool}`. Show the user the diff. Pushing the deployment is not covered by this guide; apply it in the Orchestrator UI, after step 7 has confirmed the rule.
5. **The body is the whole `data` object read in step 1, with the new rule added to its zone pair. Not a body with one zone pair.** With `merge` false, `data.map1` replaces every zone pair of the segment pair in `map`; a body holding one pair deleted all the others on the lab. Using the `api_get` results from step 1 (no call yet), copy the complete `data`, find your pair at `data.map1.<srcZoneId>_<dstZoneId>` (the `map` query is the segment pair `srcSeg_dstSeg`; the keys inside `map1` are zone pairs), add `.prio."<priority>": {"match": {...}, "set": {"action": "deny"}, "comment": "...", "gms_marked": true, "misc": {}}`, keep every existing priority (including the 65535 default) and leave every other zone pair untouched. Set `options` `{"merge": false, "templateApply": true}`. Before showing it, compare the zone-pair keys of `data.map1` with step 1: they must be the same set, plus your pair only if it is new.
6. Show the user the full body, the pair name and the list of zone pairs it contains (all of step 1's). After a yes, call `api_write` `POST /vrf/config/securityPolicies` with query `map` set to the segment pair key (`srcSeg_dstSeg`) you read in step 1, never a zone pair key: the same `^\d+_\d+$` form, but posting there with `merge` false wipes the zone pairs of a different segment pair. Without segmentation, use the template group route instead. First check the step 1 `GET /template/templateSelection`: a template that is not selected is not applied, so if `securityMaps` is missing, show the user the list with it added and, after a yes, call `api_write` `POST /template/templateSelection` (needs `templateGroup`; body the plain list of names). Then change only the `securityMaps` template: show the user the diff and tell them that saving the group pushes to every appliance associated with it. After a yes `api_write` `POST /template/templateGroups` (needs `templateGroup`; `name` the same) with `{"name": "<group>", "templates": [{"name": "securityMaps", "valObject": <its step 1 `value`, edited>}]}`. Do not post the whole group back (see [template group](template-group.md) step 4).
7. Read back: `api_get` `GET /vrf/config/securityPolicies` (`map`; on the template route `GET /template/templateGroups` with `templateGroup`) and `GET /securityMaps` (`nePk`, which can lag the Orchestrator by more than 15 seconds, so re-read before calling it a failure); compare priority, match, action and comment of your rule, and confirm every old rule and every other zone pair is still present. Check rule hits later with `GET /stats/aggregate/securityPolicy`.
8. Rollback, in this order: (a) if the user pushed the interface move, they undo it in the Orchestrator UI, and you confirm with `api_get` `GET /deployment` (`nePk`, `cached` false) that no interface sits in the new zone; (b) after a yes, `api_write` `POST /vrf/config/securityPolicies` with the whole original `data` from step 1, every zone pair (`merge` false), and query `map` = the same segment pair key as in step 6, or on the template route `POST /template/templateGroups` (`templateGroup`) with only the `securityMaps` template and its step 1 `value` as `valObject`, and, only if step 6 added `securityMaps` to the selection, `POST /template/templateSelection` with the step 1 selection (each save pushes to the associated appliances; step 8 of [template group](template-group.md)); (c) `api_write` `POST /zones` with the original global list (`deleteDependencies` false), which removes every per-segment copy of the new zone; compare `GET /zones/vrfSegmentZonesMap` with the step 1 read. Re-read each and diff against the step 1 snapshot.

## Verify
- `GET /zones` equals the intended list and no zone was lost; `GET /zones/vrfZonesMap` shows zones per segment.
- The pair holds the new rule at the right priority and all earlier rules; `GET /securityMaps` shows the same on the appliance.
- A test flow behaves as intended (`GET /flow`, filter by `zone1`); see [flows](../cards/flows-stats.md) and, for DoS protection, [protection profile](../cards/firewall-protection-profile.md).
