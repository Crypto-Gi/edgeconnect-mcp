# Build a template group and apply it

> **Reference only.** Every step below was run on Orchestrator 9.7.1 (ECOS 9.6.2.1 lab appliances and an ECOS 9.6.4.0 production appliance, test objects only) between 2026-10-16 and 2026-10-18. Your version and configuration can behave differently: read first, show the change, get a yes, and verify each step yourself.

Create a template group, choose which templates it carries, set its priority and associate appliances. Saving a group pushes it to every associated appliance, so editing an existing group is a live change; on the lab, changes were applied within about a minute of association. Background: [template groups](../cards/templates-groups.md).

## Before you start
- Decide the split: global items in the Default Template Group, small groups for the rest (for example Security Policies, Branch QoS).
- Test on lab appliances first. To try a change safely, clone a group: `POST /template/templateGroups` with query `templateGroup` = the new name and body `{"name": "<source group>", "templates": []}`. The clone gets the source's templates but not its selection, so set the selection afterwards (step 4).
- Priority: when two groups set the same template, the last group in `templateGroupsPriorities` wins. A conflicting change was applied within about a minute of association.
- Associating appliances can interrupt traffic (overlapping sections are removed and rewritten). Do it in a window, and not while orchestration is paused (maintenance mode).
- GET returns secrets empty (NAC key, user passwords). Never post a group you read back as a whole: the save fails with HTTP 500. Leave templates that hold secrets alone.
- Lab names: `ztest_group`, one lab appliance (`nePk` from `GET /appliance`).

## Steps
1. Call `api_get` on `GET /template/templateGroups` (names only with `namesOnly`), then with `templateGroup` set to read the group you will change, `GET /template/templateGroupsPriorities` for the order and `GET /template/applianceAssociation` (`nePk`) for what each appliance already carries. Keep these as the rollback snapshot, including `GET /template/templateSelection` (`templateGroup`) and the `value` of every template you will change in an existing group. A template's content is in `value`; its `valObject` reads null.
2. Call `describe_operation` on `POST /template/templateCreate` (body `name`, `comment`, `templates`) and `POST /template/templateGroups` (needs `templateGroup`; body `name`, `comment`, `templates`). Call `find_operations` with "template" if a template name is unclear.
3. Create the group: show the user the body, and after a yes call `api_write` `POST /template/templateCreate` with `{"name": "...", "comment": "..."}`. The new group holds all 46 default templates with an empty selection. The `comment` goes only to the audit log; the group's comment reads back null.
4. Choose templates: read `GET /template/templateSelection` (needs `templateGroup`), then after a yes `api_write` `POST /template/templateSelection` (needs `templateGroup`; body is a plain list of template names). To change one template, first `api_get` `GET /template/templateGroups` with `templateGroup` set to the group (for a group created in step 3 this is its first read) and take that template's `value`. Show the user the old and new content and, after a yes, call `api_write` `POST /template/templateGroups` (`templateGroup` = the group name, `name` the same) with only that template: `{"name": "<group>", "templates": [{"name": "<template>", "valObject": <that value, edited>}]}`. Templates you leave out are kept. Copy the `value` you read into `valObject`, because GET returns the content in `value` and leaves `valObject` null.
5. Set the order: show the user the full ordered list (the last group wins), and after a yes call `api_write` `POST /template/templateGroupsPriorities` with `{"priorities": [...]}`: the list as read in step 1 with the group placed where it should win. Read it back with `GET /template/templateGroupsPriorities`.
6. Associate: show the user the appliance and the complete `templateIds` list (it replaces the appliance's whole list, so include the groups read in step 1). After a yes call `api_write` `POST /template/applianceAssociation` with query `nePk` and body `{"templateIds": ["Default Template Group", "..."]}`. `POST /template/applianceAssociation2` also works for many appliances. The association clears alarms only until the next check (a critical count went 6, 5, 6 within 20 seconds), so do not read an empty alarm list as success.
7. Read back: `api_get` `GET /template/applianceAssociation` (`nePk`), `GET /template/templateGroups` (`templateGroup`) and `GET /template/history` (needs `nePk`, `latestOnly` true; false returns null) until each template shows a recent apply; on the lab, changes were applied within about a minute of association. The group name in `GET /template/history` can be wrong (the lab labelled every apply "Default Template Group"), so check the content on the appliance, not the label.
8. Rollback: after a yes, in this order: `api_write` `POST /template/templateGroups` (`templateGroup` = its name) with only the templates you changed, each with its step 1 `value` as `valObject` (the step 4 shape; never the whole group), and `POST /template/templateSelection` with the step 1 selection for any existing group you edited (each save pushes to its associated appliances); `POST /template/applianceAssociation` with the step 1 `templateIds`; `POST /template/templateGroupsPriorities` with the old order; and for a group you created `POST /template/deleteTemplateGroup` (body `templateGroup`, `comment`; the Default Template Group cannot be deleted). Re-read each against the snapshot.

## Verify
- `GET /template/applianceAssociation` matches the intended `templateIds` for each appliance.
- `GET /template/history` (`nePk`, `latestOnly` true) shows the templates applied; `GET /template/history/groupList` (`nePk`) lists the groups.
- `GET /template/templateGroups` shows the group with its siblings intact; compare name and template list, not user passwords (they read back empty).
- Spot-check the effect on the appliance (for example `GET /appliance/rest` with `nePk` and url `dnsProxy/config` or `resolver`) and that tunnels stayed up: `GET /tunnels2/bonded` (`nePk`).
